# AGENTS.md

Guidance for anyone — human or AI — working in this repository.

## Purpose

Dressing Room is a digital-closet and AI outfit rater app (Expo + Supabase), built as a portfolio demo. What works now: the Expo Router app shell (five tabs, glass tab bar, en/es), strict TypeScript, lint, tests, a closet-grid scroll-performance harness, and a Supabase-backed accounts system — email/password and social (Google, Apple) sign-in, a three-step onboarding flow, row-level-security-protected profiles, an editable Profile tab sharing its form with onboarding, and the closet: burst-camera and gallery capture through a resumable on-device upload queue (background removal, resize, upload), AI attribute extraction in an Edge Function (a mock Claude locally), a review queue that asks only what the AI doubted, and a garment detail to edit, set the status of, replace the photo of, or delete a garment. Outfits: Today (the day's weather, an optional occasion and the "feeling lucky" list from the `lucky-list` function, with "Another" and "I'll wear it"), Build (an outfit picked piece by piece from the available garments) and the rating screen (the `rate-outfit` function's Jev score with a Claude fallback, reasons, a swap, Save and "I'll wear it"), against mock Jev and Open-Meteo services locally. Insights: the Closet tab's Stats (period KPIs, most worn, colors, closet balance, the unused-for-6-months list with "Wear it" and "Donate") and Diary (a month calendar of logged wears, each deletable), all computed on the device from garments and wears. For you (the `for-you` function: 3–5 staples the closet is missing, each with a store search). Account privacy in the Profile tab: data export (the `export-data` function's JSON through the share sheet) and account deletion (the `delete-account` function, which also revokes Sign in with Apple's token, stored at sign-in by `apple-token`).

## Expo has changed — do not trust your training data

Expo ships breaking changes every SDK release. APIs you remember are likely renamed, moved, or removed. Before writing any code that touches an Expo, EAS, or React Native API:

1. Read the major version of the `expo` package in `package.json`.
2. Fetch the matching versioned docs: `https://docs.expo.dev/versions/v<major>.0.0/`
3. For anything else, fetch `https://docs.expo.dev/llms.txt` — an index of all Expo docs with corrections to common LLM misconceptions (append `.md` to a doc page's path to fetch it as Markdown). Follow its links to the specific page you need; never answer from memory.

Docs for agents: `https://docs.expo.dev/llms.txt`

- `pnpm start` — start the dev server.
- `pnpm ios` / `pnpm android` — start the dev server targeting a platform.
- `pnpm typecheck` — `tsc --noEmit`.
- `pnpm lint` — `eslint .`.
- `pnpm test` — `jest --selectProjects app scripts functions` (unit tests only; no Docker needed).

- `node integration/mockAnthropic.ts --serve <fixture>` — keep the mock Claude running for a manual check in the simulator (see "Mock Claude" under Local backend).
- `node integration/mockServices.ts --serve [--level <0..1>] [--temp <°C>]` — keep the mock Jev and Open-Meteo running for a manual check of Today and the rating in the simulator (see "Mock Jev and Open-Meteo" under Local backend).
- `pnpm test:int` — `jest --selectProjects integration --runInBand`: `src/auth`'s email/password and session flows, the cross-user RLS boundary (profiles, garments, photos), `profileRepository`'s server-clock completion and language round-trip, `garmentRepository` (uploads, signed URLs, photo versions, review, delete), garment attribute extraction end to end (trigger → pg_net → Edge Function → mock Claude), the outfit functions end to end (`lucky-list`, `rate-outfit` and `for-you` through the gateway against the mock Jev, Open-Meteo and Claude: caches, quota, RLS, `log_wear`), and the account functions (`apple-token`, `export-data` and `delete-account` against the mock Apple: the stored token, the export's rows and photo URLs, the deletion, its cascade and a retry), against a running local Supabase (`pnpm db:start && pnpm db:reset && pnpm env:local` first). Not part of `pnpm test`; CI runs it in its own `database` job (`.github/workflows/ci.yml`). Run it manually when touching auth, RLS, profile or garment persistence, the extraction function, the outfit functions or the account functions. See `docs/testing.md` for how the Jest projects and pgTAP fit together.
- `pnpm perf:generate [count=500]` — write the performance fixture thumbnails (WebP) to `.perf-fixtures/` (gitignored).
- `pnpm perf:serve [port=8787]` — serve `.perf-fixtures/` over HTTP and print every LAN URL, labeled by network interface.
- Fixture mode: start the app with `EXPO_PUBLIC_PERF_FIXTURES_URL=<url printed by perf:serve>` (e.g. `EXPO_PUBLIC_PERF_FIXTURES_URL=http://127.0.0.1:8787 pnpm expo run:ios`). The Closet tab then shows 500 fixture thumbnails, a disabled upload CTA, and the frame-stats HUD (tap: reset; long-press: also clear expo-image's memory and disk caches). Unset or empty, the Closet shows the signed-in user's real garments. The value is inlined at bundle time, so restart Metro after changing it.
- `pnpm check:expo` / `pnpm expo install --fix` — run during Expo SDK upgrades, after the 3-day `minimumReleaseAge` allows the new versions; informational, not a CI gate (see Supply-chain hardening).
- `pnpm db:start` / `pnpm db:stop` — start/stop the local Supabase stack (Docker, via OrbStack). `db:start` (and `db:start:ci`) run `scripts/db-start.ts`, which generates the local Apple test key first (see "Mock Apple" under Local backend) and then runs `supabase start`.
- `pnpm db:start:ci` — the lean stack CI starts: everything `db:test`, `db:types` and `test:int` need (Postgres, Auth, REST, Storage, Kong, postgres-meta, Mailpit, Edge Runtime), without Studio, Realtime, analytics or the image proxy.
- `pnpm db:reset` — reset the local database to the committed migrations and seed.
- `pnpm db:test` — run pgTAP database tests (`supabase test db`).
- `pnpm db:types` — regenerate `src/lib/database.types.ts` from the local schema.
- `pnpm env:local` — write `.env.local` from the running local stack's `supabase status -o env`.
- `pnpm check:supply-chain` — fail if `pnpm-workspace.yaml` loses `trustPolicy: no-downgrade` or `minimumReleaseAge`, or gains a `trustPolicyExclude` (CI's quality job runs it).

Run `pnpm typecheck && pnpm lint && pnpm test` before declaring any task done.

## Folder map

- `src/app/` — Expo Router routes; every file here is a screen, `_layout.tsx` files define navigators. Keep non-route code (components, hooks, utils) outside `src/app/`. `(tabs)/` holds the five tabs (`index.tsx` is Today, `build.tsx` is Build, `for-you.tsx` is For you). The root Stack in `_layout.tsx` also registers, inside the signed-in guard and without the tab bar: `camera`, `review`, `garment/[id]`, `rate` (mockup 01 screen 3, pushed from Today and Build as `/rate?ids=<comma-separated garment ids>[&occasion=<occasion>]`) and `city` (Today's city, a modal sheet).
- `src/ui/` — shared UI components not tied to a single route. `charts/` holds the Stats charts (mockup 04): `KpiTile`, `HorizontalBars` (most worn; bars grow with reanimated unless reduced motion is on, rows tappable) and `ProportionBar` (the colors, real garment hexes, each segment and legend entry tappable).
- `src/i18n/` — translation tables; `en` is the source of truth, `es` is the only non-English file in the repo (see Conventions).
- `src/closet/` — closet domain logic (items, outfits, wear counts). `ClosetProvider` (`useCloset`: the garments, signed thumbnail URLs, an offline copy in kv `closet.v1.<userId>`, and `usePendingPolling`, a 5 s refresh while an extraction is pending) and `UploadQueueProvider` (`useUploadQueue`: enqueue, counts, retry/discard, and `pause`/`clear`/`resume` for account deletion; runs the queue on mount, enqueue, foreground, reconnect and at the next backoff, never while the user's account deletion is unconfirmed (`account.deleting.<userId>`); on mount, foreground and reconnect it only verifies such a deletion with `confirmPendingDeletion`, never deleting without a tap) wrap the signed-in navigator in `src/app/_layout.tsx`, keyed by user. The closet also refreshes on foreground and reconnect. Both drop late results once their user is gone (unmounted, or another account's session active), and the queue steps refuse to upload or commit an item under another account's session (a retryable `SessionMismatchError`). `closetSelectors.ts` holds the pure derivations (active vs donated garments, stale pending, review queue, the fields review asks about, slot counts, grid cells with the slot and color filters). The Closet tab has three segments (`SegmentTabs.tsx`): Items (the grid), Stats (`StatsSegment.tsx`: period chips, KPI tiles, most worn, colors, balance and the unused-for-6-months list with Wear it / Donate, computed by `src/stats/` from the closet and a year of wears) and Diary (`DiarySegment.tsx`: a Monday-first month calendar with each worn day's thumbnail, the latest wear's first top or one-piece; a tapped day's wears with their pieces, occasion and score, and Delete, which removes the wear row and clears today's worn record). `GarmentFields.tsx` has the per-field chip editors (`FieldEditor`, which can be shown disabled), the read-only `ConfirmedRow` and `changedFields` (the save patch: only the fields that differ), used by the review queue (`src/app/review.tsx`) and the garment detail (`src/app/garment/[id].tsx`). `GarmentPhoto.tsx` is the full photo over a transparency checkerboard, signed on demand (again whenever `photo_version` changes) and cached by `photo_version`. `leaveToCloset.ts` is the shared back action of the review queue and the garment detail (back, or the closet when a deep link left no history). `garmentRepository.ts` is the garment data layer (list, signed photo URLs, photo uploads, insert, edits, review confirmation, delete — photos before the row). `upload/` is the photo upload queue: `queueStore.ts` (SQLite persistence; new garments and photo replacements; `clearQueue` drops one user's rows and copies), `runQueue.ts` (stages, backoff, concurrency 2; `pauseQueue` lets a stage in flight finish and starts nothing more for that user until `resumeQueue`; a stopped item keeps its attempts and is due at once), `cutout.ts` (the only caller of `modules/garment-cutout`), `preparePhoto.ts` (cut-out, one decode capped at 784 px saved as WebP 0.8, and a 256 px WebP 0.7 thumbnail built from that image), `queueSteps.ts` (the real prepare/upload/commit steps) and `permanentUploadError.ts` (a rejected upload that retrying can't fix).
- `src/auth/` — the auth service (`authService.ts`, a barrel over `emailAuth.ts` and `socialAuth.ts`), session state (`AuthProvider`/`useAuth`, which also exposes the signed-in email, reconciles the device language preference with `profile.language` once per sign-in, keeps a user signed in on an offline launch from the stored session, and, when a session ends or another user signs in, drops the kv data of any account whose deletion was under way, via `forgetInterruptedDeletions`; that path leaves the upload queue's local photo copies, see the NOTE in `deletionMarker.ts`), `deviceState.ts` (per-account facts kept on the device for offline launches: the last known onboarding status and a language choice still waiting to be saved; `forgetAccount` drops both for a deleted account) and `useSignOut` (sign-out with a visible failure message; offline it falls back to a local-only sign-out). `emailAuth.ts`'s `signOutLocally` is the sign-out after an account deletion: a local-scope sign-out that never fails, clearing the stored session directly when supabase-js can't finish. `emailAuth.ts`/`socialAuth.ts` default their `client` parameter to `src/lib/supabase.ts`'s real `supabase` singleton, the same pattern `src/profile/profileRepository.ts` uses; `integration/`'s Jest project maps that import to a stub instead (see `jest.config.ts` and `integration/lib-supabase.stub.ts`).
- `src/profile/` — `profileRepository.ts` (`getProfile`; `saveProfile`, an update of only the changed columns, never an upsert; `completeOnboarding`, stamped by the server clock), Body validation (`validation.ts`, same ranges as the DB CHECKs), the body-type helper (`bodyType.ts`), `useCurrentCity` (expo-location, when-in-use only), `useClothingType` (the profile's clothing type for garment editors, `everything` until read), `OnboardingProvider` (re-reads the profile before any onboarding step renders so a failed launch-time read can never overwrite a finished profile with defaults), and the shared editable form: `profileDraft.ts` (the form state, its mapping to columns, and the changed-fields diff) plus `ProfileForm.tsx` (`ClothingSection`, `BodySection`, `StyleSection`), used by both the onboarding steps and the Profile tab.
- `src/lib/` — the Supabase client (`supabase.ts`: SQLite-backed session storage, a 12 s request timeout from `fetchWithTimeout.ts` — 60 s for storage uploads, not signing or listing — and `readStoredSession`), generated `database.types.ts`, `requestResult.ts` (`runRequest`: maps a write's outcome to `network`/`invalid`/`unknown`, which each repository turns into its own message keys), and `kv.ts` (the only `expo-sqlite/kv-store` caller; `kvKeys` lists every key, for the deletion cleanup).
- `src/outfits/` — the outfit features shared by Today, Build and the rating screen. `aiClient.ts` (`rateOutfit`, `fetchLuckyList` and `fetchForYou`, thin wrappers over the `rate-outfit`, `lucky-list` and `for-you` functions that map their errors to a small `AiError` union, and `localDate`, the device's calendar day sent with each call), `outfitRepository.ts` (`logWear`, the idempotent `log_wear` RPC with a client-generated wear id reused on retry, and `saveOutfit`, the `save_outfit` RPC), `outfitDisplay.ts` (`SLOT_ORDER`/`orderPieces`, the display order of an outfit's pieces, `pieceLabel`, "Blusa · Negro", and `formatWeather`, Today's weather line), `buildSelection.ts` (Build's pure selection: `selectGarment` keeps one garment per slot, a one-piece and top/bottom exclude each other and only one bag, hat or accessory is kept, so a built outfit has at most five pieces against `rate-outfit`'s six; `canRate`, `selectionIds`, and `retainSelection`, which drops pieces that are no longer available), `useLuckyList.ts` (`useLuckyList`, Today's list with its debounced closet-driven refetches, shown from the stored list while it fetches and kept with an "offline" note when the network fails, and `useTodayOccasion`, the day's occasion kept in kv), `storedLucky.ts` (the last good lucky list per occasion for the day, in kv `today.lucky.<userId>`, so Today is readable offline), `useForYou.ts` (`useForYou`, the For you tab's ideas in the app's language, fetched on focus one request at a time, shown from the stored answer while it fetches and kept with a note when a fetch fails), `storedForYou.ts` (the last good For you answer per language, in kv `forYou.ideas.<userId>`), `wornToday.ts` (`useWornToday`, the outfits logged with "I'll wear it" today, kept in kv `outfit.worn.<userId>` by their sorted garment ids, which Today and the rating screen both read and write so an outfit shows "Logged ✓" on both, also after a restart; the diary's Delete calls `unmarkWornToday` so a deleted wear of today can be logged again), `OutfitStack.tsx` (an outfit's rows: thumbnail, label, wear count), `ScoreRing.tsx` (the rating ring and its loading placeholder) and `types.ts` (the functions' response types, re-exported from their `handler.ts`).
- `src/stats/` — the Stats and Diary data, all computed on the device (no AI cost). `periods.ts` (local `YYYY-MM-DD` day math anchored in UTC: `periodRange` for week / month / 6 months, `monthGrid`, the Monday-first calendar), `statsModel.ts` (pure derivations from the garments and wears in memory: `activeGarments` (not donated), `kpis`, `mostWorn`, `colorShares`, `slotBalance` with its insight, `unusedSixMonths`, `diaryByDay`) and `wearsRepository.ts` (`listWears`, the user's wears in a date range joined to their garments, and `deleteWear`, Diary's Delete; the trigger lowers the counts).
- `src/account/` — the Profile tab's Privacy actions. `accountClient.ts` (`deleteAccount`, `verifyAccount` (Auth's view of the session token: gone, exists or unknown; no function call) and `exportData`, thin wrappers over the `delete-account` and `export-data` functions, and `exportFileName`, `dressing-room-export-YYYY-MM-DD.json`; the session's token is sent explicitly; deleted means the function's `{ outcome: 'deleted' }`, or a 401 for which Auth answers `user_not_found` to that same token (a retry after a lost 200); any other 401, or no session, is `reauth`, never deleted), `deletionMarker.ts` (the kv marker `account.deleting.<id>`, `deleting:<ms>` or `reauth:<ms>` with the time it was written (any `deleting`/`reauth` value counts; an untrusted time is stamped anew at the next check), written before the call so a lost answer isn't forgotten; `forgetInterruptedDeletions`), `deletionFlow.ts` (`runDeletion`, only from the user's tap: mark, pause the queue, call; deleted → clear the queue, `signOutLocally`, the kv cleanup; `reauth` → marker `reauth` and a local sign-out keeping the queue and kv; any other failure keeps the marker and the blocked queue, since the server may have finished. `confirmPendingDeletion`, the provider's check on mount, foreground and reconnect: `verifyAccount` only; gone → the same local cleanup, exists more than `DELETION_SETTLE_MS` (10 min, above the function's wall clock) after the marker → the marker goes and the queue runs, else the marker stays. One run per user at a time), `forgetAccount.ts` (`forgetAccountOnDevice`: every kv key with the user's id as a dot-separated segment — `closet.v1.<id>`, `outfit.worn.<id>`, `today.lucky.<id>`, `forYou.ideas.<id>`, each `today.occasion.<id>.<date>` — plus `deviceState`'s entries; new per-user kv keys must keep the `<name>.<id>[.<more>]` shape to be cleared) and `usePrivacyActions.ts` (one flow at a time; export: the share sheet must be available, earlier exports in the cache directory are replaced, then `expo-sharing`'s share sheet as `public.json`; delete: two confirms, then `runDeletion`, with a "Sign in again, then delete your account again to finish." alert on `reauth`, and on any other failure a message that the deletion couldn't be confirmed and photo uploads are paused).
- `src/perf/` — the on-device frame-stats harness (UI-thread frame callback, stats, HUD).
- `src/test/` — shared Jest helpers (e.g. the FlashList mock); never imported by app code.
- `.perf-fixtures/` — generated fixture thumbnails (gitignored; see `pnpm perf:generate`).
- `supabase/functions/` — Supabase Edge Functions. Seven functions: `extract-attributes` (garment attributes from a photo, called by the insert trigger), `rate-outfit` (a Jev rating of a picked outfit, with a Claude fallback and a swap), `lucky-list` (the day's ranked "feeling lucky" outfits), `for-you` (3–5 staples the closet is missing, ranked by new outfits × a Jev fit, with Claude lines or template keys and a store-search query), `apple-token` (exchanges the Sign in with Apple authorization code for the refresh token and stores it in `apple_tokens`, only when the id_token's Apple user is the caller's own Apple identity; called fire-and-forget by `src/auth/socialAuth.ts`), `delete-account` (removes the caller's photos, revokes the Apple token, then deletes the auth user, whose rows cascade; safe to retry) and `export-data` (the caller's profile, garments, outfits with items, wears and 7-day signed photo URLs as one JSON document). See `docs/database.md`'s "Account deletion and data export" for the last three. `_shared/` holds runtime-neutral modules: `catalog.ts` (the garment enums, categories → slots, occasions, seasons), `extraction.ts` (the Claude extraction request and response sanitizer), `weather.ts` (the Open-Meteo forecast and geocoding URLs and parsers, weather bands and conditions, the location key), `outfitRules.ts` (the outfit rules, missing slots, candidate generation and the pre-score), `rating.ts` (the Jev questions and levels, answer parsing, the composite score, labels and reasons), `fallbackRater.ts` (the Claude fallback rater's request and parser), `archetypes.ts` (the For you staples, about 40 per clothing type), `forYou.ts` (For you's combinatorial gain, Jev fit, ranking, Claude lines with template fallbacks and the store-search query), `searchTerms.ts` (the en/es store-search words for the category and color enums), `apple.ts` (Sign in with Apple's server calls: the ES256 client secret signed with WebCrypto from the `.p8` key, the `/auth/token` code exchange with the id_token's Apple user (`appleSubject`, issuer and audience checked) and the `/auth/revoke` call, plus `appleEnvFrom`, which reads the `APPLE_*` secrets) and `userContext.ts` (what the user-called functions share: the caller, profile and garments read with the caller's token, the PostgREST helpers with the user's or the service role's headers, the cached weather, the quota, the result caches, the Jev and Claude calls with their timeouts). Each function folder has a runtime-neutral `handler.ts` (tested under the `functions` Jest project) and a Deno-only `index.ts`. `deno-env.d.ts` types the few Deno APIs `index.ts` uses. No third-party imports. Prompts, schema and costs: `docs/ai.md`.
- `modules/` — local Expo native modules, autolinked from this folder (no npm package). `garment-cutout/` removes a garment photo's background on-device (iOS 17+ Vision foreground masks, Android ML Kit subject segmentation) and writes a cropped PNG with alpha to the caches directory. It decodes the source at most 2048 px on the longest side (EXIF applied) before segmenting, so 48 MP photos stay within memory. On Android the manifest asks Play services to download the segmentation model at install time; until it's there, `cutOut` requests it again and resolves `null`. Its `index.ts` loads the module with `requireOptionalNativeModule`, so a build without it gets `null`. App code calls it only through `src/closet/upload/cutout.ts`'s `cutOutGarment`, which never throws and returns `null` whenever there is no cut-out. Native changes need a rebuild (`pnpm expo run:ios`), not just Fast Refresh.
- `scripts/` — repo tooling (TypeScript, run with Node's native type stripping — no `.js`/`.mjs` sources).
- `integration/` — `*.int.test.ts` Jest suites that run against a live local Supabase (plain Node, no Expo/React Native — see `pnpm test:int` above and `helpers.ts`'s module doc for why `src/auth/emailAuth.ts` is imported directly rather than through `authService.ts`'s barrel). `lib-supabase.stub.ts` is mapped over `src/lib/supabase.ts` by `jest.config.ts`'s `integration` project, so the default-client path in `emailAuth.ts`/`socialAuth.ts` throws loudly instead of touching native modules if a test ever omits its client; `expo-file-system.stub.ts` does the same for `garmentRepository.ts`'s file read (integration tests upload bytes through `uploadGarmentPhotoBytes`). `mockAnthropic.ts` (port 54499) and `mockServices.ts` (port 54498: Jev, the Open-Meteo forecast and geocoding, Apple's `/auth/token` and `/auth/revoke`) stand in for the external APIs the functions call.

## Conventions

- Everything in English, except `src/i18n/es.ts`.
- Comments only where intent isn't obvious. A deliberate simplification gets one `NOTE:` line naming its ceiling and upgrade path.
- `pnpm` (pinned to an exact 11.x in `packageManager`); Node `>=24`. Never `npm`/`yarn`/`bun`.
- TypeScript strict mode plus `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`, `noImplicitOverride`, `verbatimModuleSyntax`, `erasableSyntaxOnly`, `allowImportingTsExtensions`, with `noEmit` — no build step, no `.js`/`.mjs` source files.
- Lint: typescript-eslint `strictTypeChecked` + `eslint-plugin-security` recommended + `eslint-plugin-react-hooks` recommended (see Supply-chain hardening for why not `eslint-config-expo`).
- App identity (provisional until the owner picks a name): display name "Dressing Room", slug `dressing-room-app`, scheme `dressingroom`, bundle id / package `com.aabv21.dressingroom`.
- Light-only appearance (`userInterfaceStyle: "light"`) — v1 has no dark palette.
- Wear counts are always spelled out ("never worn" / "1 wear" / "N wears"; es: "sin usar" / "1 uso" / "N usos"), never "N×".
- CTAs are anchored pill buttons, 48pt tall minimum, 44pt hit targets everywhere.
- No secrets in the app yet. Never put keys in `EXPO_PUBLIC_*`: they are inlined into the bundle.

## Supply-chain hardening

Package management is pnpm, pinned in `package.json`'s `packageManager` to an exact `11.x` version. `pnpm-workspace.yaml` holds the settings pnpm 11 reads instead of `.npmrc`:

- `minimumReleaseAge: 4320` — refuses to install any package version (including transitive) published less than 3 days ago, so a newly-compromised release has a window to be caught and pulled before this repo can pull it in.
- `minimumReleaseAgeExclude: []` — no package is exempt from the age gate above.
- `trustPolicy: no-downgrade` — fails an install if a package's trust evidence (provenance/trusted publishing) regresses from an earlier release.
- `blockExoticSubdeps: true` — only a direct dependency may resolve from a git or tarball URL; every transitive dependency must come from the registry.
- `strictDepBuilds: true` with `dangerouslyAllowAllBuilds: false` — a dependency's install/postinstall script fails the install unless it's explicitly approved in `allowBuilds`.
- `engineStrict: true` — a dependency whose `engines` range excludes this repo's Node fails the install instead of warning.
- `allowBuilds` lists only packages a real `pnpm install` proved need their build script, each with a one-line reason: `@parcel/watcher` (`jest-haste-map`'s file watcher; links a platform binary) and `unrs-resolver` (`jest-resolve`'s native resolver; same).

**`eslint-config-expo` is deliberately not used.** It pulls in `eslint-import-resolver-typescript`, whose only SDK-58-compatible version at the time had a trust-evidence regression this repo's `trustPolicy` correctly caught, with no newer or older in-range version to fall back on and no scoped exception the owner had reviewed. This repo instead composes `typescript-eslint`'s `strictTypeChecked`, `eslint-plugin-security`'s `recommended`, and `eslint-plugin-react-hooks`' flat `recommended-latest` directly in `eslint.config.ts` — no Expo-specific lint rules are lost that matter for a TypeScript-strict, React-Native-only (no web target) app at this stage.

**`pnpm check:expo` (`expo install --check`) is informational, not a CI gate.** It compares every installed package against the single latest version on the npm registry, with no awareness of `minimumReleaseAge` — so it will always flag a package whose newer release exists but is still too young to install under this repo's hardening. Run it (or `pnpm expo install --fix`) during a deliberate Expo SDK upgrade, after the candidate versions have cleared the 3-day age gate, not as part of the regular `typecheck`/`lint`/`test` gate.

**Updating a dependency:** edit `package.json`, run `pnpm install` (not `--frozen-lockfile`) to update `pnpm-lock.yaml`, run the gate below, and commit both files together. `pnpm install --frozen-lockfile` (what CI runs) installs exactly what the lockfile pins and does **not** re-check `trustPolicy` or `minimumReleaseAge`, so a lockfile change must always come from a local `pnpm install`/`pnpm update` with these settings on — never a hand-edited or externally generated lockfile. CI's `pnpm check:supply-chain` (`scripts/check-supply-chain.ts`) fails if `pnpm-workspace.yaml` loses `trustPolicy: no-downgrade` or `minimumReleaseAge`, or gains any `trustPolicyExclude`. `minimumReleaseAge` will refuse a version published too recently — wait it out or pin an older compatible version instead.

## Local backend

The local backend is Supabase running in Docker (via OrbStack), driven only through the `supabase` npm devDependency (`pnpm exec supabase …` / the `db:*` scripts) — never a global or Homebrew install.

- `pnpm db:start` — starts the local stack (Postgres, Auth, Storage, Studio, Mailpit, Edge Runtime). First run pulls Docker images and can take several minutes. The Edge Runtime serves every function under `supabase/functions/` at `http://127.0.0.1:54421/functions/v1/<name>` and reloads on file changes; its logs are in `docker logs supabase_edge_runtime_dressing-room-app`.
- `pnpm db:reset` — drops and recreates the local database from `supabase/migrations/` and `supabase/seed.sql`.
- `pnpm db:test` — runs the pgTAP suite under `supabase/tests/`.
- `pnpm db:types` — regenerates `src/lib/database.types.ts` from the local schema; commit the result alongside the migration that changed it.
- `pnpm db:stop` — stops the stack. Always leave it stopped when you're done.
- `pnpm env:local` — writes `.env.local` (gitignored) from `supabase status -o env`: the app gets `EXPO_PUBLIC_SUPABASE_URL` / `EXPO_PUBLIC_SUPABASE_ANON_KEY`; `SUPABASE_SERVICE_ROLE_KEY` and `SUPABASE_DB_URL` are for scripts and integration tests only. It merges rather than clobbers: it only ever writes those four keys (in that fixed order), and keeps every other line already in `.env.local` as-is — so a hand-set `EXPO_PUBLIC_GOOGLE_WEB_CLIENT_ID`/`EXPO_PUBLIC_GOOGLE_IOS_CLIENT_ID` (see "Social sign-in" below) survives a re-run.
- Local email (signup confirmations, password-reset codes) is caught by Mailpit at http://127.0.0.1:54424 instead of being sent.
- Password reset uses a 6-digit code (`{{ .Token }}` in `supabase/templates/recovery.html`), not a link.
- Passwords need at least 8 characters on the server too (`minimum_password_length` in `supabase/config.toml`); the hosted project's Auth settings must match.
- NOTE: `requestPasswordReset` reports `over_email_send_rate_limit` as sent, and GoTrue uses that code for the project-wide hourly email cap too (`[auth.rate_limit].email_sent`), so the integration session must set the hosted email and SMTP/SES limits generously. See `docs/testing.md`.
- Functions: the local secrets are literal, local-only values in `supabase/config.toml`'s `[edge_runtime.secrets]` (`EXTRACT_WEBHOOK_SECRET`, `ANTHROPIC_API_KEY`, `ANTHROPIC_BASE_URL`, `TYPESAFE_API_KEY`, `TYPESAFE_BASE_URL`, `OPEN_METEO_URL`, `OPEN_METEO_GEOCODING_URL`, `APPLE_TEAM_ID`, `APPLE_KEY_ID`, `APPLE_CLIENT_ID`, `APPLE_BASE_URL`; `APPLE_PRIVATE_KEY` is read from the environment, see "Mock Apple"), applied when the stack starts, so restart it (`pnpm db:stop && pnpm db:start`) after changing them. `SUPABASE_URL`, `SUPABASE_ANON_KEY` and `SUPABASE_SERVICE_ROLE_KEY` are injected by the runtime.
- Mock Claude: locally `ANTHROPIC_BASE_URL` is `http://host.docker.internal:54499`, where `integration/mockAnthropic.ts` listens while `extraction.int.test.ts` and `outfits.int.test.ts` (For you's lines) run. Nothing local ever reaches the real Claude API; with no mock running, extraction ends `failed`. For a manual check in the simulator, `node integration/mockAnthropic.ts --serve <fixture>` keeps it running and answers every call with `supabase/functions/_shared/__tests__/fixtures/claude-<fixture>.json` (`ok`, `low-confidence`, …).
- Mock Jev and Open-Meteo: locally `TYPESAFE_BASE_URL`, `OPEN_METEO_URL` and `OPEN_METEO_GEOCODING_URL` are all `http://host.docker.internal:54498`, where `integration/mockServices.ts` serves `POST /v1/systemone`, `GET /v1/forecast` and `GET /v1/search` while `outfits.int.test.ts` runs; `TYPESAFE_API_KEY` is a placeholder. Nothing local ever reaches the real TypeSafe or Open-Meteo APIs; with no mock running, `rate-outfit` falls back to the (mock or absent) Claude and the weather is unknown. `rate-outfit`, `lucky-list`, `for-you`, `apple-token`, `delete-account` and `export-data` run with `verify_jwt = true`, so they need a signed-in user's token; the anon key passes the gateway but has no user, and the function answers 401.
- Mock Apple: locally `APPLE_BASE_URL` is `http://host.docker.internal:54498` too, where `mockServices.ts` serves Apple's `POST /auth/token` and `POST /auth/revoke` while `account.int.test.ts` runs. The local team, key and client ids are made up. No key is committed: `config.toml` reads `APPLE_PRIVATE_KEY = "env(LOCAL_APPLE_PRIVATE_KEY)"`, and `pnpm db:start`/`db:start:ci` (`scripts/db-start.ts`) generate a P-256 key into gitignored `supabase/.temp/apple-test-key.pem` when it's missing (kept across restarts, never registered with Apple) and pass it to `supabase start`; `account.int.test.ts` reads the same file to verify the client secrets. Nothing local can reach or authenticate to the real Apple. A bare `pnpm exec supabase start` leaves `APPLE_PRIVATE_KEY` unset (checked), so `apple-token` answers `skipped` and deletion skips the revoke, as on a hosted project without the secrets. With no mock running, `apple-token` answers `exchange_failed` and deletion logs `revoke_failed` and goes on. Without the `APPLE_*` secrets (a hosted project before the owner session), `apple-token` answers `skipped` and deletion skips the revoke.
- Vault: the garments insert trigger (`public.request_garment_extraction()`) reads the function URL and webhook secret from the Vault secrets `extract_attributes_url` and `extract_webhook_secret`, which `supabase/seed.sql` creates locally on every `pnpm db:reset` (the URL uses Kong's container name, since pg_net runs inside the db container). See `docs/database.md`'s "Extraction trigger".
- NOTE: the owner's integration session sets the hosted values: the two Vault secrets (the real function URL and a random secret, via `vault.create_secret`) and `pnpm exec supabase secrets set EXTRACT_WEBHOOK_SECRET=<same secret> ANTHROPIC_API_KEY=<key>`. Until then hosted inserts queue no extraction and garments reach review with empty fields.
- NOTE: the outfit functions need the hosted TypeSafe key: `pnpm exec supabase secrets set TYPESAFE_API_KEY=<key>` (the URLs default to the real TypeSafe and Open-Meteo hosts when unset). Until then they fail every call with a 500, since `index.ts` requires the key (`rate-outfit` and `for-you` also require `ANTHROPIC_API_KEY`).
- **The service-role key never goes in `src/`.** It bypasses Row Level Security; it belongs only in scripts, CI secrets, and test setup, read from `supabase status -o env` or `.env.local`, never bundled into the app.

## Social sign-in

- NOTE: `app.json`'s `@react-native-google-signin/google-signin` plugin config has a placeholder `iosUrlScheme` (`com.googleusercontent.apps.REPLACE_IN_INTEGRATION_SESSION`). The live owner session that sets up the real Google OAuth client replaces it with the project's actual reversed iOS client ID from Google Cloud Console — Sign in with Google on iOS will not work until then.
- Two more `EXPO_PUBLIC_*` vars are allowed in the app bundle: `EXPO_PUBLIC_GOOGLE_WEB_CLIENT_ID` and `EXPO_PUBLIC_GOOGLE_IOS_CLIENT_ID`. OAuth client IDs are not secrets — they identify the app to Google the way a bundle id does — so this doesn't widen the "no secrets in `EXPO_PUBLIC_*`" rule above. `src/auth/socialAuth.ts`'s `signInWithGoogle` reads both (literal `process.env.EXPO_PUBLIC_*` member expressions, same inlining constraint as the Supabase URL/key) and calls `GoogleSignin.configure({ webClientId, iosClientId })` lazily on first use; if either is missing it resolves `{ ok: false, error: 'auth.error.unknown' }` and logs a dev-only `console.warn` rather than attempting to sign in. The integration session fills both into `.env.local`/`.env.example` with the project's real Google OAuth client IDs.
- `@react-native-google-signin/google-signin` v17's free `signIn()` does not send a custom nonce — see `src/auth/socialAuth.ts`'s module doc (summary: no nonce on Android, a hidden one on iOS that this library doesn't expose; sending one anyway made every sign-in fail against GoTrue's OIDC check). `signInWithIdToken` is therefore called with no `nonce` for Google (Apple's flow is unaffected and still uses one). NOTE: the integration session must set `[auth.external.google].skip_nonce_check = true` in `supabase/config.toml` (and the hosted project's equivalent setting) for Google sign-in to succeed — see the NOTE above that config key. Google sign-in has no nonce replay protection from this client today. Upgrade path: a library version that exposes iOS's nonce, or Universal Sign In (this package's paid tier).

## Permissions

- `app.json`'s `plugins` array order is load-bearing for iOS permission strings and Android permissions, not just cosmetic ordering: `expo-image-picker` must stay listed **before** `expo-camera`. Each permissions-owning plugin's Info.plist mod runs in that same array order, and the later one's non-`false` value always wins (`@expo/config-plugins`' `applyPermissions`: `infoPlist[key] = permissions[key] || infoPlist[key] || defaultDescription`), so `expo-camera` must run last to make its real `NSCameraUsageDescription` the one that sticks.
- `expo-image-picker` must **not** set `cameraPermission: false`. That option is not merely "skip setting iOS's default string" — on Android it also calls `withBlockedPermissions(['android.permission.CAMERA'])`, which adds a `tools:node="remove"` manifest entry that wins over *any* other plugin's `uses-permission` add at Gradle manifest-merge time, including `expo-camera`'s own. Setting it removes Android's camera permission from the built app entirely, breaking the camera even though `expo-camera` is installed and configured. Leave `cameraPermission` unset on `expo-image-picker` (its own default iOS string is irrelevant there, since `expo-camera`'s later mod overwrites it per the point above).
- `locales/en.json` and `locales/es.json` (referenced from `app.json`'s top-level `expo.locales`) hold the localized iOS usage-description strings (`NSCameraUsageDescription`, `NSPhotoLibraryUsageDescription`, `NSLocationWhenInUseUsageDescription`) as `{"ios": {...}}`, one file per locale, independent of whatever the config plugins set as the base (English) Info.plist default. `ios.infoPlist.CFBundleAllowMixedLocalizations: true` is required for iOS to pick a locale's translated string instead of always showing the base one. Verify any change here with `pnpm expo prebuild -p ios --clean` (read the generated `ios/<app>/Info.plist` and `ios/<app>/Supporting/<locale>.lproj/InfoPlist.strings`) and `pnpm expo prebuild -p android --clean` (read `android/app/src/main/AndroidManifest.xml` for `android.permission.CAMERA`) — `ios/`/`android/` are gitignored CNG output, safe to delete afterward.

## Branches and pull requests

- `main` holds released code and is the default branch; `develop` is the integration branch. Both take changes only through a pull request with CI green, and repository rulesets block direct pushes, force pushes, and deletion.
- Work on a short-lived branch from `develop` (`feat/…`, `fix/…`, `docs/…`, `chore/…`) and open the pull request into `develop`, titled in Conventional Commits form. It's squash-merged, so the title becomes the commit.
- A release is a pull request from `develop` into `main`, merged with a merge commit, then tagged `vX.Y.Z` with a GitHub release.
- Dependabot opens its pull requests against `develop`.
- Commits use the GitHub `noreply` address, never a personal email: set `git config user.email` to it in this clone.

## Definition of done

- `pnpm typecheck && pnpm lint && pnpm test` all pass locally.
- No secrets anywhere in the diff.
- Commits follow Conventional Commits, on a descriptively named branch.
