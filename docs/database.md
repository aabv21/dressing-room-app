# Database: schema, RLS and storage

The local backend is Supabase (Postgres 17) run via `pnpm db:*` scripts (see `AGENTS.md`). This
document covers the `public.profiles`, `public.garments` and `public.usage_counters` tables, their
enums, the signup trigger, row level security, the `garments` storage bucket, and what account
deletion and data export do to them. See
`docs/testing.md` for how these are exercised by pgTAP and the integration Jest project.

## Tables and enums

### `public.profiles`

created automatically on signup — see [Signup trigger](#signup-trigger) below. Clients never insert

### `public.outfits`, `public.outfit_items`, `public.wears` (Plan 4)

One outfit is a set of garments, logged either through a wear (`public.log_wear()`) or saved on its
own (`public.save_outfit()`). `public.outfits (id uuid primary key default gen_random_uuid(),
user_id uuid not null default auth.uid() references auth.users on delete cascade, saved_at
timestamptz, created_at timestamptz not null default now())` — `saved_at` is null unless the outfit
was explicitly saved. `public.outfit_items (outfit_id uuid references public.outfits on delete
cascade, garment_id uuid references public.garments on delete cascade, primary key (outfit_id,
garment_id))` is the join table between an outfit and its garments; it has no `user_id` of its own,
so its policies check the referenced outfit/garment instead. `public.wears (id uuid primary key
default gen_random_uuid(), user_id uuid not null default auth.uid() references auth.users on delete
cascade, outfit_id uuid not null references public.outfits on delete cascade, worn_on date not
null, occasion public.occasion, score smallint check (score between 0 and 100), created_at
timestamptz not null default now())` is one row per logged wear of an outfit.

Indexes: `outfits_user_id_idx` on `outfits (user_id)`; on `outfit_items`, `outfit_items_garment_id_idx`
on `outfit_items (garment_id)` — no separate index on `outfit_id` alone, since the primary key
`(outfit_id, garment_id)` already leads with `outfit_id` and serves that lookup; on `wears`,
`wears_user_id_idx` on `wears (user_id)`, `wears_user_id_worn_on_idx` on `wears (user_id, worn_on
desc)` (backs Stats' and Diary's reads of a user's wears by date, `src/stats/wearsRepository.ts`'s
`listWears`) and `wears_outfit_id_idx` on `wears (outfit_id)` (backs the wear-count trigger's and
the RPCs' per-outfit lookups).

**Clients never insert or update these tables directly in the documented path** —
`public.log_wear()` and `public.save_outfit()` (below) are the RPCs the app calls. Clients may
`select` all three (own rows only) and `delete` their own `wears` rows (Plan 5's diary undo); there
is no delete policy on `outfits` or `outfit_items` (and `delete` is revoked outright on both — see
"RLS and storage rules" below), and no update policy anywhere on any of the three (`update` is
revoked outright on all three). Because both RPCs are `security invoker`, the privilege to insert is
still there — gated by each table's own insert policy — so a direct client insert of the caller's
own row is technically possible; it's just never the app's path, and it carries its own self-only
integrity gaps (see "RLS and storage rules" below). See [Logging a wear](#logging-a-wear) and
[Wear count maintenance](#wear-count-maintenance-trigger) below.

**Deleting an outfit does not decrement any garment's wear count — a cascade trap.** `outfit_items.outfit_id
references public.outfits on delete cascade`, so deleting an `outfits` row deletes its
`outfit_items` rows as part of the same statement, before Postgres processes `wears.outfit_id
references public.outfits on delete cascade`'s cascade into `wears` and fires
`wears_maintain_counts` for each deleted wear. By the time that trigger runs, the `outfit_items`
rows it would join through to find "which garments" are already gone, so its `where … and g.id in
(select oi.garment_id from public.outfit_items oi where oi.outfit_id = old.outfit_id)` matches
nothing and no garment's `wear_count`/`last_worn_at` moves. There is no client path to delete an
`outfits` row (no delete policy, and delete is revoked outright — see above), so this can't happen.
Diary's Delete (`deleteWear`) deletes only the `wears` row, through `wears_delete_own`, and the
trigger lowers the counts; the outfit stays. Any future outfit deletion must delete its `wears`
rows first and only then the `outfits` row — never the other order.

### `public.rating_cache`, `public.lucky_cache`, `public.weather_cache` (Plan 4), `public.for_you_cache` (Plan 5)

Server-only caches for the rating, feeling-lucky, weather and For-you Edge Functions; no client ever
reads or writes them. `public.rating_cache`, `public.lucky_cache` and `public.for_you_cache` share
the same shape: `(user_id uuid references auth.users on delete cascade, cache_key text, result jsonb
not null, created_at timestamptz not null default now())`, primary key `(user_id, cache_key)`.
`public.weather_cache` is not user-scoped (weather is shared across users at the same place and
hour): `(location_key text not null, hour timestamptz not null, payload jsonb not null)`, primary key
`(location_key, hour)`. All four have RLS enabled with **no policies at all** and `revoke all` from
both `anon` and `authenticated` — same "no API surface" pattern as `usage_counters` below, except
nothing reads or writes them through a `security definer` function either; only `service_role` (the
Edge Functions) ever touches them, bypassing RLS entirely as that role.

`for_you_cache` holds one row per user: each new entry deletes the user's rows under every other key
once it is written (best effort, so a failed delete can leave an older row until the next write).

NOTE: the other three grow without bound. An expired degraded entry is overwritten only when the
same key is asked for again, any other entry never expires, and nothing deletes old rows: a new
day, occasion, closet edit or profile save writes new keys, and `weather_cache` gains a row per
place and hour. At 4 users that's a few thousand small rows a month, with user deletion cascading
the user-scoped two away. Upgrade path: a scheduled cleanup with `pg_cron` (for example a daily
`delete from public.rating_cache where created_at < now() - interval '30 days'`, the same for
`lucky_cache`, and `delete from public.weather_cache where hour < now() - interval '2 days'`), in
an append-only migration.

### `public.apple_tokens` (Plan 5)

Server-only: one row per user who signed in with Apple, holding the refresh token account deletion
revokes with Apple before removing the `auth.users` row. `(user_id uuid primary key references
auth.users on delete cascade, refresh_token text not null, created_at timestamptz not null default
now())`. RLS is enabled with **no policies at all** and `revoke all` from both `anon` and
`authenticated` — same server-only pattern as the caches above; only `service_role` (the
`apple-token` and `delete-account` Edge Functions) ever touches it. See "Account deletion and data
export" below for how the row is written and used.

### `public.usage_counters`

Backs the extraction quota (100 per user per UTC day — `EXTRACTION_DAILY_LIMIT` in
`supabase/functions/extract-attributes/handler.ts`), the Plan 4 rating quota (50 per user per UTC
day), the Plan 4 feeling-lucky quota (10 per user per UTC day) and the Plan 5 For-you quota (1 per
user per UTC day, counting cache misses only).
`(user_id uuid references auth.users on delete cascade, day date, kind quota_kind, count integer
not null default 0 check (count >= 0))`, primary key `(user_id, day, kind)`. `quota_kind` has four
values: `extraction` (Plan 3), `rating`/`lucky` (Plan 4, added by `alter type … add value` in
`20261108120000_outfits_wears_caches.sql`) and `for_you` (Plan 5, added the same way in
`20261109000000_insights_account.sql` — each `add value` is its own statement, and the new value
isn't referenced anywhere else in that migration, so it commits in the same transaction as the rest
of it; Postgres only forbids using a brand new enum value in the same transaction that added it, not
adding it). RLS is enabled with **no policies at all** and `revoke all` from
both `anon` and `authenticated` — the table has no API surface of its own; every read and write goes
through `public.consume_quota()`.

`public.consume_quota(p_user_id uuid, p_kind public.quota_kind, p_limit integer) returns boolean` is
`security definer` with `set search_path = ''`, `execute` revoked from `public`, `anon` and
`authenticated`, and granted only to `service_role` — only the extraction function calls it, never
a client. It returns `false` immediately if `p_limit < 1`; otherwise it upserts the row for
`(p_user_id, today in UTC, p_kind)`, incrementing `count` only `where count < p_limit`, and returns
whether a row was actually written (an `on conflict … do update … where …` whose `where` excludes
the conflicting row makes `returning` produce no row, not a row holding `false` — the function
reads that absence as `false` via `coalesce`). Each call therefore does at most one state change:
either the counter moves up by one and the function returns `true`, or nothing changes and it
returns `false`.

## RLS and storage rules

### `public.profiles`

RLS is enabled with two policies for `authenticated`, both comparing `user_id = (select auth.uid())`
(wrapped in `select` so Postgres evaluates it once per statement, not once per row):

- `profiles_select_own` — `select`
- `profiles_update_own` — `update`, with the check in both `using` and `with check`

**There is no insert policy** (the first migration had one; `20261107171540_profiles_value_limits_and_write_rules`
dropped it): the signup trigger creates every row, so a client insert — including the insert half
of an upsert — is rejected with `42501`. **There is no delete policy** either: a client delete
removes nothing, and a profile row only goes away via `on delete cascade` from `auth.users`
(account deletion goes through the `delete-account` function; see "Account deletion and data
export"). The `anon` role has no privileges on the table at all (nothing reads profiles while
signed out), and neither client role has `truncate`, `trigger` or `references`.

### `public.garments`

RLS is enabled with four policies for `authenticated`, all comparing `user_id = (select
auth.uid())` (`insert` and `update` are also narrowed by column grants — see below):

- `garments_select_own` — `select`
- `garments_insert_own` — `insert`, with `with check`
- `garments_update_own` — `update`, with the check in both `using` and `with check`
- `garments_delete_own` — `delete`

`revoke all on public.garments from anon` (no signed-out access), and `truncate`, `trigger` and
`references` are revoked from both `anon` and `authenticated`.

**Column grants narrow insert and update further than the row-level policies do.** After `revoke
insert, update on public.garments from authenticated` (removing Supabase's default wide-open
privileges), the client gets back only:

- `grant insert (id)` plus `grant insert (user_id)` (migration `…_garments_insert_user_id.sql`)
  — a client insert supplies `id` and may state `user_id` (default `auth.uid()`); every other
  column takes its own default (`status = 'available'`, `extraction_status = 'pending'`, empty
  arrays, `photo_version = 1`, `wear_count = 0`, …). The app always states the owner it queued the
  photo for, so `garments_insert_own`'s `with check (user_id = (select auth.uid()))` rejects
  (`42501`) a commit that runs after a sign-out or user switch instead of the default filing the
  garment under whoever is signed in; the upload queue retries that error rather than failing the
  photo.
- `grant update (category, colors, pattern, material, formality, seasons, warmth, fit, occasions,
  status, photo_version, reviewed_at)` — the client can edit a garment's attributes and status, but
  **can never write** `user_id`, `extraction_status`, `uncertain_fields`, `wear_count`,
  `last_worn_at`, `created_at` or `updated_at`. Attempting to `set extraction_status = …` (or any
  other ungranted column) in the same `update` statement as a granted column raises `42501` for the
  whole statement, even if the row would otherwise be the caller's own — a column-privilege
  violation is checked before row filtering, so it fails the same way regardless of which row is
  targeted.
- `grant update (pinned_on)` (Plan 5, `20261109000000_insights_account.sql`) — the client can also
  set `pinned_on` on their own garment. Unused-for-6-months' "Wear it" sets it to tomorrow's local
  date; `lucky-list` includes the garment in that day's outfits when any complete outfit with it
  passes the rules. Nothing clears it automatically — the day simply passes.

`created_at`/`updated_at` follow the same pair of trigger functions `profiles` uses:
`garments_set_updated_at` (`public.set_updated_at()`) sets `updated_at = now()` before every
update, and `garments_keep_created_at` (`public.keep_created_at()`) copies the old `created_at`
back over whatever an update sends — both revoked from direct `execute` by clients, same as on
`profiles`.

### `public.outfits`, `public.outfit_items`, `public.wears` (Plan 4)

RLS is enabled on all three, all comparing against `(select auth.uid())`:

- `outfits` — `outfits_select_own` (select), `outfits_insert_own` (insert, `with check`). No update
  or delete policy, and (see below) `update`/`delete` are also revoked at the table-privilege level.
- `outfit_items` — `outfit_items_select_own` (select) via `exists (select 1 from public.outfits o
  where o.id = outfit_id and o.user_id = (select auth.uid()))`; `outfit_items_insert_own` (insert,
  `with check`) requiring both the referenced outfit and the referenced garment to be the caller's.
  No update or delete policy, and `update`/`delete` are revoked at the table-privilege level too.
- `wears` — `wears_select_own` (select), `wears_insert_own` (insert, `with check`),
  `wears_delete_own` (delete). No update policy, and `update` is revoked at the table-privilege
  level (see below) — unlike `outfits`/`outfit_items`, `delete` stays granted, since
  `wears_delete_own` is a real policy (Plan 5's diary undo).
  `wears_insert_own`'s `with check` requires **both** `user_id = (select auth.uid())` **and**
  `exists (select 1 from public.outfits o where o.id = outfit_id and o.user_id = (select
  auth.uid()))` — checking `user_id` alone would let a caller insert a wear naming their own
  `user_id` but someone else's `outfit_id` (a uuid they could have seen or guessed from
  elsewhere), and the `security definer` wear-count trigger would then update that other user's
  garments. The outfit-ownership check closes that; see "Wear count maintenance" below for the
  trigger's own, second layer of defense against the same thing.

`revoke all on <table> from anon` and `revoke truncate, trigger, references on <table> from anon,
authenticated` on all three. **Unlike an earlier draft of this migration, a missing policy alone is
not what blocks `update`/`delete` here.** Supabase's default ACL (`pg_default_acl`) grants
`authenticated` every table privilege on a new table, including `update` and `delete` — with no
policy for either, an `update` with no matching row count (not a `42501`) rather than a policy
error, exactly like `garments_rls.test.sql`'s cross-user update/delete demonstrates for a table that
*does* have other policies. Since there is no legitimate update path on any of the three tables, and
no delete path on `outfits`/`outfit_items`, the migration also runs `revoke update, delete on
public.outfits, public.outfit_items from authenticated` and `revoke update on public.wears from
authenticated` — so a client `update` anywhere, or a `delete` on `outfits`/`outfit_items`, raises
`42501` (a real privilege error) rather than silently touching zero rows. There is no column-grant
narrowing here the way `garments` has: `insert` stays at the row-policy level because
`public.log_wear()`/`public.save_outfit()` are `security invoker` and rely on the caller's own
insert privilege and policies (see below) — the policies above are the only gate on insert, and
they're already as narrow as the RPCs need.

**Direct inserts are self-only, not fully equivalent to the RPCs.** Because insert privilege and the
row policies are the whole gate, a client that insists on inserting directly into `outfits`,
`outfit_items` or `wears` instead of calling `log_wear()`/`save_outfit()` can still build a
logically broken state the RPCs never produce: an `outfits` row with no `outfit_items`, a `wears`
row for an outfit nobody put any garments in, or an `outfit_items` row whose outfit has no `wears`
row at all. Every one of those rows would still only ever be the caller's own (RLS guarantees that
part), so this is a self-inflicted data-integrity gap, never a cross-tenant one — but it's real, and
it's the reason `log_wear()`/`save_outfit()` are documented as the only intended path rather than
merely "a convenience."

### `public.rating_cache`, `public.lucky_cache`, `public.weather_cache` (Plan 4), `public.for_you_cache`, `public.apple_tokens` (Plan 5)

RLS is enabled with **zero policies** on all five, and `revoke all on <table> from anon,
authenticated` — same "no RLS-mediated access path at all" pattern as `usage_counters` below, except
nothing reads or writes them through a `security definer` function either: only `service_role`
(the rating, lucky, weather and For-you Edge Functions for the caches; `apple-token` and
`delete-account` for `apple_tokens`) ever touches them, bypassing RLS entirely as that role. A
direct `select`/`insert`/`update`/`delete` from `authenticated` or `anon` is rejected by the table
grant revoke before RLS is even consulted.

### `public.usage_counters`

RLS is enabled with **zero policies**, and `revoke all on public.usage_counters from anon,
authenticated` — this table has no RLS-mediated access path at all; it is only ever touched inside
`public.consume_quota()`, which runs as its definer (effectively `postgres`) and therefore bypasses
RLS entirely. A direct `select`/`insert`/`update`/`delete` from `authenticated` or `anon` is
rejected by the table grant revoke before RLS is even consulted.

### `storage.buckets` / `storage.objects` (`garments` bucket)

The `garments` bucket is created by SQL insert (not the dashboard), so it is reproducible from
migrations:

- `public = false` (private — every read goes through an authenticated request)
- `file_size_limit = 2097152` (2 MiB)
- `allowed_mime_types = ['image/webp', 'image/png', 'image/jpeg']`

Object paths are namespaced per user: `<user_id>/<anything>`. Four policies on `storage.objects`
(select, insert, update, delete) all require:

```sql
bucket_id = 'garments'
and (storage.foldername(name))[1] = (select auth.uid())::text
```

A user can never read, write, or delete another user's objects, even with a guessed path — the
folder-name check runs server-side on every request.

### Writing a profile: update, never a partial upsert

`saveProfile` sends `update … where user_id = <me>` with only the columns that changed, and treats
an update that reaches no row as an error. Never use an upsert for a partial patch: Postgres checks
an `INSERT … ON CONFLICT DO UPDATE`'s proposed insert row against every CHECK constraint *before* it
finds the conflict, and that row has only the patch's columns. Saving just `city_lat`, for example,
failed `profiles_city_lat_lon_pair_check` even though the stored row had both coordinates. The
client also sends the coordinates as a pair (both, or both null when the city is cleared) and each
style or occasion once. (Duplicates aren't blocked in the database: a CHECK can't contain a
subquery, and the helper function it would need would also be exposed as an RPC.)

`created_at` can't be rewritten either: `public.keep_created_at()` (`before update`) copies the old
value back over whatever an update sends.

### Extraction trigger

`public.request_garment_extraction()` (migration `20261108025224_garment_extraction_trigger`,
redefined by `20261108110716_garment_extraction_trigger_never_blocks_insert`) fires
`after insert on public.garments for each row` as the trigger `garments_request_extraction`. It is
`security definer` with `set search_path = ''`, so it can read the Vault, and `execute` is revoked
from `public`, `anon` and `authenticated`. It reads two secrets from `vault.decrypted_secrets`:

- `extract_attributes_url` — the `extract-attributes` Edge Function URL as the database sees it;
- `extract_webhook_secret` — the shared secret the function checks in the `x-webhook-secret`
  header (its `EXTRACT_WEBHOOK_SECRET`).

With both present it calls `net.http_post` (the `pg_net` extension, created `with schema
extensions`; its functions live in the `net` schema) with body `{"garment_id": <id>}` and a 5 s
timeout. If either secret is missing it does nothing, so inserts keep working on a project that
isn't configured yet; those garments stay `pending` until the app's 10-minute rule sends them to
review. Any error inside it (the Vault read, or `net.http_post` rejecting the URL or misbehaving
after a pg_net change) is caught the same way: `exception when others` raises a warning carrying
only the SQLSTATE (never the message, which could echo the URL) and returns the row, so the insert
commits and the garment takes the same path to review.

pg_net queues the request in the inserting transaction and sends it after commit. So a rolled-back
insert calls nothing, and an `insert … on conflict do nothing` duplicate (the app's retried upload)
inserts no row and fires no trigger. The 5 s timeout only ends pg_net's wait for the response: the
function keeps running, finishes its own 30 s Claude timeout and writes the result back
(`net._http_response` then shows `timed_out` for that request, which is expected).

**Local values** come from `supabase/seed.sql`, recreated by every `pnpm db:reset`:
`extract_webhook_secret = 'local-only-not-a-secret'` (matching `[edge_runtime.secrets]` in
`supabase/config.toml`), and `extract_attributes_url =
'http://supabase_kong_dressing-room-app:8000/functions/v1/extract-attributes'`. pg_net runs inside
the db container, where `127.0.0.1:54421` is the container itself, so the URL uses Kong's container
name on the stack's Docker network. `integration/extraction.int.test.ts` proves the whole path.

**Hosted values** are set by hand in the owner's integration session, never from a file in this
repo:

```sql
select vault.create_secret('https://<project-ref>.supabase.co/functions/v1/extract-attributes', 'extract_attributes_url');
select vault.create_secret('<random secret, e.g. openssl rand -hex 32>', 'extract_webhook_secret');
```

and the function's own secrets with
`pnpm exec supabase secrets set EXTRACT_WEBHOOK_SECRET=<same random secret> ANTHROPIC_API_KEY=<key>`
(`ANTHROPIC_BASE_URL` stays unset there, so the function uses `https://api.anthropic.com`).

### Logging a wear

`public.log_wear(p_wear_id uuid, p_garment_ids uuid[], p_worn_on date, p_occasion public.occasion
default null, p_score smallint default null) returns uuid` is the documented, and only intended,
way to log a wear. It is `security invoker` with `set search_path = ''`, `execute` revoked from
`public` and `anon`, granted to `authenticated` only. Being `security invoker` (not `security
definer`) is deliberate: the actual inserts into `outfits`, `outfit_items` and `wears` run as the
calling role, so they're still gated by those tables' own insert policies — the function doesn't
bypass RLS, it just saves the client three round trips and the chance of a half-written outfit.

**Idempotent on `p_wear_id`** (Review Focus 5: double-tapping "I'll wear it", or retrying after a
lost response, must log exactly one wear). The app generates `p_wear_id` once per tap
(client-side, a plain random uuid) and sends the same value on every retry of that same tap.

1. `select id from public.wears where id = p_wear_id` — if a row comes back, the wear already
   exists and is visible to the caller (RLS means visible ⇒ the caller's own), so the function
   returns that id immediately and inserts nothing. This is the retry path: the first call's insert
   landed but its response was lost, so the retry just re-confirms the same id.
2. Otherwise, validates `p_garment_ids`: raises `22023` (`invalid_parameter_value`) if it's null,
   has fewer than 2 elements, or contains a duplicate (`cardinality` compared against a `distinct
   unnest` count).
3. Checks ownership: `select count(*) from public.garments where id = any(p_garment_ids)` runs under
   the caller's own RLS, so it only counts garments that are both in the array *and* the caller's
   own. If that count is short of the array length — some id doesn't exist, or belongs to someone
   else, the two cases are indistinguishable from outside and deliberately so — it raises `42501`
   (`insufficient_privilege`).
4. Inserts an `outfits` row (defaults: `user_id = auth.uid()`, `saved_at` stays null), one
   `outfit_items` row per garment id, and one `wears` row with `id = p_wear_id` (`worn_on`,
   `occasion`, `score` from the arguments), returning the new wear's id.

**If `p_wear_id` belongs to someone else's wear,** step 1's select finds nothing (RLS hides it), so
the function falls through to step 4's insert, whose primary key conflict on `wears.id` then raises
— a uuid collision with another user's row is vanishingly unlikely in practice (the app generates a
fresh random uuid per tap), but the behavior is still "raise," never "silently attach to or
overwrite someone else's wear."

`public.save_outfit(p_garment_ids uuid[]) returns uuid` is the sibling RPC for saving a combination
without logging a wear: same garment-array validation and ownership check as steps 2–3 above (not
idempotent — it has no caller-supplied id to check against), but it inserts only `outfits` (with
`saved_at = now()`) and `outfit_items`, no `wears` row, and returns the outfit id instead. Calling
it never creates a `wears` row and never fires `wears_maintain_counts`, so it never changes any
garment's `wear_count`/`last_worn_at`.

Because both are `security invoker`, `authenticated` keeps `insert` on `outfits`, `outfit_items` and
`wears`, gated by each table's own insert policy (see "RLS and storage rules" above). A client can
therefore insert directly into any of the three tables instead of calling the RPC — but only ever
rows that pass those same policies (the caller's own `user_id`, their own outfit, their own
garment); see "RLS and storage rules" above for the self-only integrity gaps that direct path still
has. The RPCs are the app's only path in practice: they're the one place the array validation, the
idempotency check and the all-or-nothing multi-table insert live.

### Wear count maintenance (trigger)

`public.maintain_wear_counts()` fires as the trigger `wears_maintain_counts`
(`after insert or delete on public.wears for each row`). It is `security definer` with
`set search_path = ''` (so it can write `garments.wear_count`/`last_worn_at`, which no client role
can — see the garments column grants above) and `execute` is revoked from `public`, `anon` and
`authenticated` (the trigger still fires on every insert/delete; only a *direct* call is blocked).

- **On insert:** every garment referenced by the new wear's outfit (through `outfit_items`) **and
  belonging to the same user as the wear** (`g.user_id = new.user_id`) gets `wear_count =
  wear_count + 1`, and `last_worn_at` moves forward to the wear's `worn_on` if that's later than
  what's stored (`greatest(coalesce(last_worn_at, worn_on), worn_on)`, so a `null` `last_worn_at`
  is always replaced). This also bumps `updated_at` on every affected garment — see the note
  below, "Logging a wear bumps garments.updated_at," before keying any cache on that column.
- **On delete:** every garment referenced by the deleted wear's outfit **and belonging to the same
  user as the wear** (`g.user_id = old.user_id`) gets `wear_count = greatest(wear_count - 1, 0)`
  (never negative), and `last_worn_at` is recomputed from scratch as the max `worn_on` across that
  garment's *remaining* wears **by that same user** — joining `wears` back through `outfit_items`
  for that garment, excluding the row being deleted and filtering `w.user_id = old.user_id` — or
  `null` if none remain. This is a full recompute rather than "move it back one step" because a
  garment can appear in several outfits worn on different dates; only a fresh `max()` over what's
  left is correct after a delete.

**`worn_on` (a `date`) is always converted with `at time zone 'UTC'`, never a bare `::timestamptz`
cast.** A bare cast interprets the date in the database session's `TimeZone` setting, which could
in principle differ between connections (pooled connections, a future session-level `set
timezone`); pinning it to UTC means `last_worn_at` always lands on the same instant for the same
`worn_on`, regardless of what produced the connection.

**The `g.user_id = new.user_id` / `g.user_id = old.user_id` filters are defense in depth, not the
primary guard.** `wears_insert_own`'s policy (above) already stops a `wears` row from referencing
another user's outfit in the first place, so in practice every garment this trigger touches is
already the wear's own user's garment. The filters mean that even if some future change ever let a
cross-tenant `wears` row land here — a new insert path, a bug in the policy, a direct write as a
role that bypasses RLS — this `security definer` trigger still could not move another user's
`wear_count`/`last_worn_at`, because it's scoped to `g.user_id = new/old.user_id` on top of the
`outfit_items` join. Two independent layers (the policy and the trigger) have to both be wrong at
once for a cross-tenant write to happen.

A garment can be in the same outfit as other garments that are deleted independently (`garments …
on delete cascade` from `outfit_items`), but the trigger is on `wears`, not `outfit_items` or
`garments`, so deleting a garment never fires it — the garment's own row is just gone, and any
other garment that shared an outfit with it is unaffected (its own wear_count/last_worn_at came from
its own wears, not from what else was in the outfit).

**Logging a wear bumps `garments.updated_at` (confirmed empirically — see below), so neither
the rating cache (`rate-outfit`) nor the lucky fingerprint (`lucky-list`) may key on it.** The trigger's `update
public.garments set wear_count = …, last_worn_at = …` is an ordinary `update` statement, which fires
`garments_set_updated_at` (`public.set_updated_at()`, `before update on public.garments`) exactly
like any other garment update — there is nothing wear-count-specific that would exempt it. A quick
same-transaction check can look like a no-op (`now()` is stable for the whole transaction in
Postgres, so an insert and a trigger-fired update inside one transaction can share a timestamp down
to the microsecond), but across separate statements the bump is real: inserting a garment, then
(in a later statement) inserting a wear that references it through `outfit_items`, moves that
garment's `updated_at` forward. Both caches must hash each garment's *rating-relevant* columns
(`category`, `colors`, `pattern`, `formality`, `fit`, `seasons`, `warmth`, `status`) instead of
`updated_at`, or every "I'll wear it" tap would invalidate both caches for every garment in the
outfit — a quota-counted recompute (`rating`/`lucky` consume_quota) on an action that changed
nothing about how any of those garments should be rated.

### Signup trigger

`public.handle_new_user()` is `security definer` with `set search_path = ''` (every name inside it
is fully qualified — `public.profiles`, not `profiles`) so it cannot be tricked by a search_path
manipulation into writing to the wrong table. It runs `after insert on auth.users` and inserts a
bare `public.profiles` row (`user_id` only; every other column takes its default/null). The
`updated_at` trigger (`public.set_updated_at()`) is the same pattern, firing `before update on
public.profiles`.

### Onboarding completion clock

`public.stamp_onboarding_completed_at()` (migration `20261105120000_onboarding_completed_at_server_clock`)
fires `before insert or update of onboarding_completed_at on public.profiles`. When the column goes
from null to non-null it replaces whatever the client sent with `now()`, so the completion time
always comes from the server clock, never a device's. Once set, it keeps the old value: a later
write (another timestamp, or a null) cannot change it, so no client can move a finished profile
back into onboarding. The app's `completeOnboarding` sends Postgres's `'now'` literal and filters on
`onboarding_completed_at is null`.

NOTE: the trigger also blocks the service role, so an admin reset of onboarding (back to null) must
run with the trigger disabled: `set local session_replication_role = replica;` in the same
transaction as the `update` (as the table owner).

### Account deletion and data export (Plan 5)

Three Edge Functions, all `verify_jwt = true` and called by the signed-in user
(`supabase/functions/{apple-token,delete-account,export-data}/`). The service-role key is used only
inside them, never in `src/`.

- **`apple-token`** — `signInWithIdToken` keeps no Apple refresh token, and Apple's `/auth/revoke`
  needs one. Right after Sign in with Apple the app sends the credential's one-time
  `authorizationCode` (fire-and-forget, `src/auth/socialAuth.ts`); the function exchanges it at
  Apple's `/auth/token` with an ES256 client secret (`_shared/apple.ts`, signed with WebCrypto from
  the `.p8` key). The token is bound to the caller: the exchange's id_token must be issued by Apple
  (`iss`) for this app (`aud` = `APPLE_CLIENT_ID`), and its `sub` must be one of the caller's
  `auth.identities` with provider `apple` (read with the service role through
  `GET /auth/v1/admin/users/{uid}`). Only then does it upsert `public.apple_tokens (user_id,
  refresh_token)` with the service role; otherwise it stores nothing and revokes the new token, best
  effort. It answers 200 with an outcome word (`stored`, `skipped` without the `APPLE_*` secrets,
  `invalid`, `exchange_failed`, `identity_mismatch`, `lookup_failed`, `store_failed`); the token
  never leaves the server.
- **`delete-account`** — in this order:
  0. confirms the caller with `GET /auth/v1/user` and the caller's own token, before anything
     irreversible; only Auth's `user_not_found` means an earlier attempt already finished, so it
     sweeps `garments/{uid}/` once more (a photo that landed while that attempt's answer was lost)
     and answers `deleted`, with no revoke or user deletion; any other failure, a bare 404
     included, answers 500;
  1. with the service role, lists every object under `garments/{uid}/` (Storage's list, 1000 entries
     a page, the garment folders 5 at a time) and only then removes them, 1000 paths per call;
  2. revokes the `apple_tokens` refresh token with Apple, if there is one — a failed revoke (or a
     failed read of the row) is logged as `revoke_failed` and never blocks the deletion;
  3. with the service role, `DELETE /auth/v1/admin/users/{uid}`, after which every public table cascades away:
     `profiles`, `garments` (and through them `outfit_items`), `outfits`, `wears`,
     `usage_counters`, `rating_cache`, `lucky_cache`, `for_you_cache` and `apple_tokens` all
     reference `auth.users` with `on delete cascade` (pinned by `insights_account.test.sql`).
  4. once this call has deleted the user, sweeps `garments/{uid}/` one last time, best effort:
     another device (or a token that is still valid) can upload between steps 1 and 3, because the
     storage insert policy only checks the folder's uid. A failed final sweep still answers
     `deleted`; a retry sweeps again at step 0.

  Safe to retry: a failed caller check, listing, removal or user deletion answers 500 with the user
  still there, so the next attempt starts over with whatever is left; once the user is gone, a retry
  (the access token stays valid until it expires) sweeps the folder at step 0 and answers 200
  `{ outcome: 'deleted' }`; a 404 from the admin delete (a concurrent attempt won) sweeps the folder
  again and counts as deleted too; a failed sweep on either path answers 500. The uid is always the
  verified JWT's `sub`. Storage objects are removed first because nothing cascades into
  `storage.objects`.

  The app (`src/account/`) first writes the kv marker `account.deleting.<uid>`, then pauses its
  upload queue (a stage in flight finishes), so no photo lands after the listing, and sends the
  session's access token explicitly. It reports the account deleted only on
  `{ outcome: 'deleted' }`, or on a 401 for which Auth's `GET /user` with that same token answers
  `user_not_found` (a retry after a lost 200). Any other 401 (an expired token,
  `session_not_found`, a refresh token that's gone) or no session at all doesn't prove the account
  is gone, so the app tells the user to sign in again and then delete the account again
  (`reauth`), and signs out locally, keeping the queue and the kv entries (the marker turns
  `reauth`). Signing in doesn't finish anything by itself: the check below sees the account still
  there and removes the marker, and the user taps "Delete account" again. On a deletion the app
  clears the queue, signs out locally, clears every kv key under the user's id (the marker
  included) and refuses that user's later kv writes for the rest of the process, so a request still
  in flight can't write them back; then it removes the data exports from the cache directory and
  clears expo-image's memory and disk caches. Either sign-out happens only while the stored session
  is still that user's (or there is none): an answer that arrives after another account signed in
  never signs it out, and the Profile tab's Sign out is disabled while a deletion runs.
  Any other failure (network, a 500, a gateway 502/504) may come after the server already deleted
  the user, so the marker stays: the user stays signed in, is told the deletion couldn't be
  confirmed and that photo uploads are paused, and can tap again.

  While the marker exists that user's queue never runs. The marker holds its state and the time it
  was written (`deleting:<ms>` / `reauth:<ms>`). Any value whose state is `deleting` or `reauth`
  counts, whatever its time; a missing or malformed time, or one more than the settle window in the
  future, is stamped anew at the next check, so the window below starts over instead of being
  skipped.
  A launch, sign-in, return to the foreground or reconnect with the marker present only asks Auth,
  with that session's token, whether the account still exists, and never deletes anything without a
  tap: `user_not_found` gets the same local cleanup and sign-out as a confirmed deletion; the same
  user, more than 10 minutes after the marker (the function may still be sweeping storage after the
  app's 45 s timeout, up to the Edge Functions wall clock), removes the marker and lets the queue
  run; anything else keeps the marker for the next check. A session that ends while the marker says
  `deleting` (supabase-js signs out by itself once the account is gone) drops that account's kv
  data, but not the queue's local photo copies.

  NOTE: on that lost-session path the upload queue's SQLite rows and their photo copies stay on the
  device; they never upload without that user's session, and run again if the account turns out to
  exist. Upgrade path: a `queue.purge.<uid>` sweep when the queue provider mounts.
- **`export-data`** — reads `profiles`, `garments`, `outfits` (with `items:outfit_items(garment_id)`)
  and `wears` with the caller's own token, so RLS applies, in pages of 1000 (`max_rows`), and drops
  any row whose `user_id` isn't the caller's. Photo URLs are signed with the service role for 7 days,
  only for `{uid}/{garmentId}/{full,thumb}.webp` paths built from the caller's own garments (a
  missing variant is `null`, and a garment with no photo at all is left out of `photos`). The answer
  is `{ exportedAt, profile, garments, outfits, wears, photos: [{ garmentId, full, thumb }] }`.

NOTE: locally the signed export URLs start with the Edge Runtime's internal `SUPABASE_URL`
(`http://kong:8000`), so they only open after swapping in `http://127.0.0.1:54421`; hosted, it's the
public project URL. Upgrade path: a public-URL function secret, if a local export ever needs to
open on a device.

## New table checklist

Supabase's default privileges (`pg_default_acl`; `\ddp` in psql) grant `anon`, `authenticated` and
`service_role` every privilege on each new table and sequence in `public`, and `execute` on each new
function (on top of Postgres's own default `execute` for `public`). So a new table starts wide open
to the API until RLS and these revokes close it:

- `alter table … enable row level security`.
- Policies `to authenticated`, comparing against `(select auth.uid())` (not a bare `auth.uid()`).
  An `update` policy has both `using` and `with check`, so a row can't be moved to another user.
- No insert, update or delete policy the app doesn't need (a missing policy is a denial).
- `revoke all on <table> from anon` unless signed-out access is really needed.
- `revoke truncate, trigger, references on <table> from anon, authenticated`.
- `revoke execute on function <fn> from public, anon, authenticated` for every new function,
  including trigger functions (a trigger still fires; only direct calls are blocked).
- An index on the column per-user queries filter by (`user_id`), unless it's already the primary
  key.
- Tests: pgTAP for the policies and constraints, and supabase-js integration tests that user A
  can't select, update, delete or list user B's rows.
- `pnpm db:types` and commit the generated types (CI fails on drift).

## How to add a migration

```bash
pnpm exec supabase migration new <descriptive_name>
```

This writes an empty, timestamped file under `supabase/migrations/`. Write plain SQL into it —
`create table`, `alter table`, new policies, etc. Then:

```bash
pnpm db:reset   # drops and recreates the local DB from every migration + supabase/seed.sql
pnpm db:test    # runs the pgTAP suite under supabase/tests/
pnpm db:types   # regenerates src/lib/database.types.ts — commit it alongside the migration
```

**Migrations are append-only once merged.** Never edit a migration file that has already landed on
`main` — even to fix a typo. Write a new migration that corrects it instead. This keeps
`pnpm db:reset` reproducible for every other clone of the repo (and for CI) at every point in
history, and avoids a merged migration's hash diverging from what's already been applied to any
running database.

## pgTAP tests

`supabase/tests/*.test.sql` run under `pg_prove` via `pnpm db:test`. Each file wraps its assertions
in `begin; select plan(N); ... select * from finish(); rollback;` so nothing it does persists. pgTAP
is not installed by default in the local Postgres image; rather than ship it as a migration (which
would install its ~1000 functions into every environment, including the hosted database), each test
file enables it for itself as its first statement after `begin;`
(`create extension if not exists pgtap with schema extensions;`) and the closing `rollback;` removes
it again. `supabase test db` (CLI 2.122.0) also manages this on its own, so the per-file statement
is a belt-and-suspenders guard, not the only thing making pgtap available.

Tests impersonate a user without needing a real JWT, by setting the two GUCs PostgREST reads:

```sql
set local role authenticated;
select set_config('request.jwt.claims', json_build_object('sub', '<uuid>', 'role', 'authenticated')::text, true);
```

(`set local ... = <expression>` is not valid SQL for a non-literal value — `SET` only accepts
literals — hence `set_config()`, which accepts any text expression, with `is_local = true` to
scope it to the transaction like `set local` would.)

Test users are created by inserting directly into `auth.users` with explicit, fixed UUIDs inside
the test transaction; the insert fires the signup trigger, and the rollback at the end of the file
discards both the user and its profile row — no cleanup step is needed.

- `profiles_rls.test.sql` — cross-user isolation: A sees only A's row, A's update targeting B's row
  changes nothing, A can't insert (for anyone, nor upsert their own row), A's delete of their own
  row removes nothing, and the anon role can't read the table at all.
- `storage_rls.test.sql` — bucket configuration (private, 2 MiB, three MIME types) plus the same
  cross-user isolation for `storage.objects`.
- `profiles_constraints.test.sql` — every CHECK constraint rejects an out-of-range or malformed
  value (`height_cm = 300`, `waist_cm = 10`, an 11-character `top_size`, an 81-character or blank
  `city_name`, `city_lat` without `city_lon`, onboarding completed with a null `clothing_type`) and
  accepts a fully valid row; updating one coordinate of a stored pair passes.
- `profiles_onboarding_clock.test.sql` — completing onboarding (by update, or by an insert as the
  table owner) stores the server's `now()`, not the client-sent time; a second completion or a null
  keeps the original time.
- `profiles_write_rules.test.sql` — a client update can't change `created_at`.
- `garments_rls.test.sql` — cross-user isolation: B selects, updates or deletes A's garment and
  gets 0 rows/no effect, B can't insert a row claiming A as owner, and the anon role can't read the
  table at all.
- `garments_rules.test.sql` — every CHECK constraint (`formality`, `warmth`, 4 colors,
  `photo_version`) rejects an out-of-range value; an insert with only `id` gets `user_id` from the
  caller and defaults `status`/`extraction_status`; an insert stating the caller's own `user_id`
  succeeds, another user's raises `42501`, and inserting `extraction_status` raises `42501`; a
  client can't update `extraction_status`, `wear_count` or `user_id`; an update leaves
  `created_at` unchanged and moves `updated_at`.
- `usage_quota.test.sql` — `consume_quota` returns `true` up to `p_limit` and `false` after (and
  stays refused for that user and kind); a different user is tracked independently; `p_limit 0` always returns `false`; calling the
  function or reading `usage_counters` directly as `authenticated` raises a policy error.
- `garment_extraction_trigger.test.sql` — `garments_request_extraction` exists, fires only `after
  insert … for each row` and calls `request_garment_extraction()`, which is `security definer` and
  not executable by `authenticated`; with both Vault secrets set (test values, inside the
  transaction) an insert queues one `net.http_request_queue` POST carrying the garment id, the
  secret header and the 5 s timeout; with them deleted, an insert still succeeds and queues nothing;
  with a URL pg_net rejects (so queueing the request raises), the insert still succeeds and keeps
  its row.
- `outfits_wears.test.sql` — `log_wear` for A with 3 garments creates one outfit, 3 `outfit_items`

## Local backup and restore

Not exercised by CI or the automated test suites — this is a manual procedure for local
development. Dump **outside the repo** — a local DB dump can contain real account data from manual
testing and must never land in git history:

```bash
pnpm exec supabase db dump --local -f ~/dressing-room-backup.sql   # schema + data, local DB only
```

To restore into a fresh local stack: `pnpm db:reset` (migrations + seed) and then replay any data
you need from the dump with `psql "$SUPABASE_DB_URL" -f ~/dressing-room-backup.sql`, or pass
`--data-only` to `db dump` if you only want rows back on top of an already-migrated schema. This is
a local convenience, not a production backup strategy — Supabase Cloud projects get point-in-time
recovery from the platform itself.
